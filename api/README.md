# API and workers
One NestJS package with two entrypoints: `src/main.ts` for HTTP and `src/worker.ts` for background work.
Both import the same DomainModule and InfrastructureModule. Only WorkerModule registers
workers/processors; HTTP startup never starts job consumers.

## Layers

| Directory | Contains |
| --- | --- |
| src/api/rest | Controllers: protocol mapping only, no business rules |
| src/api/dto | Request body types |
| src/domain/<feature> | Use-case services and the feature's Nest module |
| src/infra/db/schema | Drizzle table definitions and relations |
| src/infra/db/repositories | Persistence for each feature |
| src/infra/db/rls.ts | Transaction helper that sets Supabase RLS session variables |
| src/infra/auth | API-key guard, scopes, credential issue/revoke/rotate (applied globally via `APP_GUARD`) |
| db/postgres/migrations | Migrations generated by `npm run db:generate` |

Create other folders (config, observability, vendor clients, queue, workers) when the first
feature needs them; see [the implementation guide](../docs/implementation-guide.md) and
[the roadmap](../docs/roadmap.md).

From the root: npm run start:api or npm run start:worker. From api/: npm run start or npm run start:worker.
Both require a root build first because API uses the shared contracts workspace.

## Calling the API

Every route requires `Authorization: Bearer <api key>`. The tenant is always resolved from the
matched credential, never from a client-supplied header — an `x-organization-id` header is
accepted only as a client-side sanity check and is rejected if it disagrees with the key. The
first credential for a new organization is issued out of band (there is no bootstrap endpoint,
since calling one would itself need a key): `npm run seed:dev-credential -- <organizationId>`.
That key carries the `admin` scope, which can then issue/revoke/rotate further keys via
`/v1/api-credentials`.
